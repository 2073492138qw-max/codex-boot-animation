## 一、优先修复的问题

### R01 / P1：安装测试可能删除真实的停用标记

证据：`scripts/Install-Startup.ps1:31` 读取真实 UserProfile 下的 disabled 并删除；`scripts/Test-Install.ps1:131` 调用该脚本，但只模拟注册表、进程等操作，没有隔离 Test-Path/Remove-Item 或运行数据路径。

影响：存在真实 disabled 文件时，测试会改变用户停用状态；安装失败的回滚也没有恢复该文件。这是上一轮新增逻辑未完整接入测试隔离的问题。代码路径已确认，本轮没有创建或删除真实标记来演示。

方案：让安装操作显式接收运行数据根目录；测试强制临时根目录；恢复启动事务开始前的停用标记状态。默认测试入口拒绝使用真实运行数据目录。

验收：在隔离目录分别放置/不放置 disabled，注入 adopt、launch、readiness 失败，比较前后字节；真实 UserProfile 保护快照不变。

### R02 / P1：测试通过的资源包无法通过安装预检

证据：`scripts/Test.ps1:71` 仅警告缺少首帧图；`scripts/Install.ps1:30` 将同一条件作为致命错误。

本轮执行只读 `Install.ps1 -CheckOnly`，实际失败：`Release media is missing: 冷启动/MiniMax_H3_00359_.mp4`。该 MP4 实际存在，缺的是 PNG。共查到 4 个目录项缺少首帧图。

方案：决定首帧是否为必需资源，并共用一份预检函数。若支持缺图时黑色过渡，安装器也应接受；若发行包要求完整封面，打包前生成封面并严格检查。错误信息应明确缺视频还是缺封面。

验收：仓库、解压包、中文及带空格路径执行同一预检；缺封面条件下测试和安装结论一致。

### R03 / P1：resident 的死亡和假死没有完整恢复闭环

证据：`src/BootPlayer.cs:803` 的 supervisor 只持续调用 EnsureWatcher；EnsureResidentPlayer 仅在 watcher 启动（480）及媒体目录变动（524）时调用。Launch（699）在管道连接失败而 resident 互斥量存在时直接丢弃事件。

影响：resident 退出而 watcher 仍在时，系统可能长期依赖冷启动兜底；闲置 IPC 不会自行恢复。resident 假死但互斥量尚在时，请求可能持续被丢弃。代码可确认这些分支，本轮未杀真实进程。

方案：明确一个生命周期管理者，以进程身份和有超时的健康响应判断状态；有限重启、退避、防重叠。恢复时采用已有 Codex 实例，不误播冷启动。不要只把“互斥量存在”视为健康。

验收：隔离环境分别模拟 watcher 退出、resident 退出、resident UI 卡住、管道满、初始化慢；恢复后只出现一份播放器及一次应播放事件。

### R04 / P2：任务完成日志仍有无界读取和跨文件阻塞

证据：`src/CompletionJournal.cs:53` 在全局 gate 内打开并读取文件；62 使用 CopyTo 直到当前末尾，随后 ToArray 和 UTF-8 转换。没有换行时偏移不推进。相比之下，导航读取已有 256 KiB 预算。

影响：大尾部会同时占用多份缓冲，未完成长行反复读；慢文件阻塞其他完成日志；事件积压还可能排队多个完成处理任务。当前没有证明发生 OOM。

方案：复用有文件身份、大小预算和部分行缓存的增量读取器；按文件隔离；合并重复读取任务；设置可观测的超长行拒绝策略。

验收：1/16/64 MiB 无换行尾部、分段 UTF-8、慢文件与正常文件并发，读取量和内存有明确上限，正常文件不被慢文件锁住。

### R05 / P2：导航文件替换后会串接旧半行

证据：`src/NavigationCursor.cs:16` 仅以新长度小于旧偏移判断截断，不识别文件替换或截断后迅速增长。

本轮使用实际已构建程序集的 NavigationCursor，在 MemoryStream 隔离复现：先读 `old\npart`，替换成 `new\nabcdef\n`，第二次实际得到 `partef\n`。这验证算法条件问题，不表示已在用户日志中发生。

方案：由文件层跟踪文件 ID/代次，替换或截断时同时重置偏移、半行、丢弃状态；对同文件截断后回长的情况补充连续性检测。

验收：替换后更短、等长、更长，截断后立即回长，部分多字节字符，以及轮转重命名。

### R06 / P2：新聊天去重状态没有按窗口隔离，双来源去重不对称

证据：`src/BootPlayer.cs:440` 的 onBlankDialogRoute、lastUiTriggerUtc、lastDesktopTriggerUtc 为 watcher 全局字段；HandleLogLine（633）没有接收窗口/进程身份。点击分支（550）只比较上次点击时间，日志分支才检查点击去重。

影响：A 窗口到空白页后，B 窗口首次到空白页可被全局状态压掉；日志先到、UIA 结果后到也存在重复派发路径。隔离调用实际 AdvanceDialogRoute，连续两个窗口的 true 状态输出为 True/False；真实双窗口操作未测。

方案：状态键包含进程创建时间及窗口/路由标识；点击和日志进入同一事件仲裁器，双向关联、有限去重；全局窗口播放互斥与事件去重分开处理。

验收：双窗口交替新建、点击先/日志先、快速双击、快捷键、冷启动后新聊天，每次真实动作可解释地播放或合并。

### R07 / P2：输入检测虽移除低级钩子，但端到端可靠性未证明

证据：`src/BootPlayer.cs:553` 用窗口左上 55% 范围筛选；`src/NewChatHitTest.cs:32` 每次候选点击启动子进程，之后 FromPoint 查询。RawMouseInput 使用处理消息时的 GetCursorPos，而非不可变点击目标。

影响：区域内普通点击也可能启动 .NET/UIA 子进程；鼠标移动、页面切换、布局改版或不同可访问性进程归属可能使实际点击目标丢失。语言列表和可选选择器改善了兼容性，但不是稳定宿主接口。

本轮可见的当天轮转日志中有 2 次日志兜底、没有 raw click 成功记录；样本不足以判定原生点击通道失效。此前自建按钮收到 Raw Input 仅证明输入送达，不证明 Codex 新聊天识别成功。

方案：先加固定原因码和采样计时，测点击到识别的 P50/P95；缓存稳定的候选按钮身份并有界失效，保留被动日志兜底；避免重新启用高频全树扫描。

### R08 / P2：四个管道监听者不等于可靠投递

证据：`src/BootPlayer.cs:647` 客户端写完就返回成功，未获播放接收确认；663/667/675 使用没有截止时间的 Dispatcher.Invoke；699 又把写入成功记录为 delivered。

影响：UI 停顿时同步命令可占满监听者；异步派发仍可能积压；日志显示 delivered 并不证明窗口已经接受或显示。单连接读取的一秒限制并没有约束 UI 执行阶段。

方案：版本化消息、请求 ID、过期时间，返回 accepted/busy/rejected；有界队列和合并策略；区分写入、接受、开始播放。UI 超时后撤销尚未执行的过期命令。

验收：静默客户端、UI 阻塞、突发 20 请求、响应丢失和重试，既无无限排队也无重复窗口。

### R09 / P2：同步日志可拖慢播放器 UI

证据：`src/RotatingLog.cs:19` 每条日志最多等待跨进程锁 500 ms，随后同步文件操作；IntroWindow 的打开、开始、进度、结束路径直接调用 IntroLog.Write。

影响：磁盘慢、轮转或其他进程持锁时，动画 UI 可等待；锁超时又会静默丢日志。ReactionTrace 的异步写入没有覆盖全部 IntroLog。

方案：有界异步日志队列，播放路径只入队；后台批量轮转；按级别合并/丢弃并记录丢弃计数，正常退出给予短暂 flush 截止时间。

验收：日志文件被占用、磁盘写入失败和写入突发时，播放器消息循环不等待日志锁。

## 二、架构与工程不足

### R10：常驻内存仍高；启动和重新扫描仍预加载全部片头

`src/MediaLibrary.cs:65` 返回启动、新聊天目录的全部 MP4；`src/BootPlayer.cs:278` 为其各建 MediaElement，346 的重新扫描再次全部加载。30 秒释放仅改善闲置持有方式，没有限制启动峰值，也没有保证进程私有内存明显下降。

现有 311.9 MiB 私有内存样本说明目标尚未达成；不能将“Close 已调用”直接等同于“内存优化完成”。也不能将 PNG/MP4 磁盘体积当作解码后内存大小。

建议先做“轻量控制进程 + 按需渲染进程”的可回退原型：默认不预热全部视频，最多热存一个；播放器闲置退出，控制进程有界拉起。这样媒体栈可随进程退出释放。是否合并 supervisor/watch 另作单变量评估；将 WPF 全塞进唯一进程会扩大崩溃影响，不能只凭进程数量决定。

验收至少包括启动峰值、空闲 60 秒内存、冷/热首帧延迟、连续 100 次播放后的增长斜率、崩溃恢复；内存和首帧延迟目标应由原型测量后确定。

### R11：构建、测试与最终发行 EXE 缺少来源绑定

`.github/workflows/ci.yml:23` 在构建/测试后恢复仓库内 EXE，Package-Release 再归档 HEAD。打包脚本会重测该 EXE，这是已有保护；但两份不同二进制都通过测试，仍不能证明发行 EXE 对应本次源码。

建议用同一次构建产物完成测试、打包、解压复测，写入 commit、构建配置和哈希清单；若保留已提交 EXE，则校验构建来源关系。增加 --version 和 --protocol-version。

当前实装源码已复制 50 文件，却没有 Build.ps1 和嵌入图标；README 仍指向已移走的 BootPlayerV2.cs。实装目录尚非完整可重建的源码包。版本号、文档和缓存的维护需要统一发布流程。

### R12：测试覆盖与生产路径已发生偏离

`src/NavigationTailPollTests.cs` 仍使用旧 NavigationLogReader，而生产 ReadNewLogLines 已使用 NavigationCursor。新增 RepairRegressionTests 覆盖部分读取器行为，但没有替代真实 watcher 的事件/尾读/目录核对交互测试。

CompletionJournal.SelfTest 会通过 TaskCompletion.OnPrompt 写真实运行目录中的随机测试状态，而不是统一隔离根目录。另见 R01 的更直接副作用。

建议拆分纯单元、隔离集成、真实媒体、人工验收四组；测试统一注入数据路径、时钟、进程启动器和文件系统适配层。新增生产链路测试优先于增加同构断言数量。

### R13：状态文件写入不是事务，清理分散且不完整

`src/CompletionStateStore.cs:29` 和 30 直接写两份 candidate；同 session 锁不能让崩溃中断具备原子性。每个 prompt 又扫描全部 candidate/claimed 清理旧文件。completion-deliveries、desktop-instances、settings-backups 没有统一保留上限。

本机只读计数：delivery 99 文件、desktop claims 213、settings backups 11，目前体积很小，不能声称已造成磁盘故障。

方案：以原子替换的单条 session 状态或具恢复规则的事务记录作为真源；清理移出 prompt 热路径，周期执行并有预算；对已完成/失败状态设保留期，保护仍在使用的去重记录。

### R14：完成动画的“成功”信号与真实画面仍有差距

`src/BootPlayer.cs:217` 在媒体时钟超过 0.18 秒时触发 CompletionStarted，并记录 first-moving-frame；没有检查生产画面像素。`src/CompletionDeliveryStore.cs` 的注释却把 receipt 描述为 moving video started。黑屏但时钟正常时，该信号不能证明画面正常。

异常记录主要保留 Message，原始异常类型/HRESULT 不完整。当前既不能宣称黑屏已根治，也不能凭此断言显卡或其他软件冲突。

方案：准确命名为 media-clock-advanced；记录固定异常类型、HRESULT 和有限内层码；保留受控媒体帧探针及人工验收。避免默认持续截图，避免记录聊天正文。

### R15：完成判定和两秒投递窗口是产品取舍，应公开说明

成功判定依赖中英文正则，可能被引用、否定、说明文和局部完成绕过或误伤。完成投递窗口 2 秒、最多 3 次，过期失败后不重新开始；测试明确锁定了“不无限迟到重播”的行为。

这不是简单把超时增大就能修好的缺陷。建议将“任务回合结束”“推断成功”“视频已接受”分别呈现，给出固定未播放原因；慢机冷启动超过预算的场景应决定是取消还是短期重试，保留用户跳过后不重播的约束。不要为了提升命中率把聊天正文持久化或发送到云端。

### R16：入口、停用、安装位置和设置耦合

CompanionLifetime.EnsureSupervisor、CompletionDelivery.PlayerPath 依赖 Windows Run 值寻找活动安装。关闭动画助手自启动也会影响恢复及播放器位置解析；这与“Codex 本体自启动”是两个开关。

未知命令模式未统一拒绝：`src/BootPlayer.cs:840` 附近可回落到默认新聊天预览，而不是返回参数错误。新增测试参数或旧缓存不识别参数时，可能出现错误播放或假阳性。

方案：活动安装位置存独立配置；明确“登录启动 / 允许自动动画 / 暂停 / 卸载”状态；CLI 白名单校验，未知参数返回非零且不启动窗口。卸载和更新都以安装身份及版本校验操作范围。

### R17：可维护性、文档及性能边界仍不足

BootPlayer.cs 混合输入、进程、WPF、完成判定、IPC 与命令路由；大量长行阻碍审查。旧按钮发现类/字段和测试仍在，但主路径已经切换。ARCHITECTURE/SECURITY/安装 README 仍描述低级钩子、旧读取器或旧日志目录；HANDOFF/NEXT_ACTION 顶部还停在 10 月 8 日。

日志每 5 秒递归枚举全部 .log，本机普通日志目录已有 108 个；navigationCursors、logOffsets、readyProcesses 等没有一致淘汰策略。16 条快速尾读上限不代表所有映射和扫描都受限。

方案：先补当前事实和清理死路径，再按职责机械拆分，不同时改行为。历史记录归档，当前交接保留短入口。目录核对设频率/总量预算，游标按文件身份和活动期淘汰。

## 三、原 14 项清单的校正

- WH_MOUSE_LL 已被 Raw Input 替换；仍保留的 owner 位置 WinEventHook 是另一种机制，不能混称全局低级鼠标钩子。
- 100 ms timer 仍在，但完整进程枚举已限到约 1 秒。不能据 timer 数字继续断言每秒 10 次全量进程查询。
- 日志已有 2 MiB 当前文件 + 1 个旧文件轮转；剩余问题是同步写入和诊断准确性。
- --prompt-hook / --stop-hook 在当前源码已实现。旧“完全没有分支”的结论已失效。
- 当前实装 hooks 中历史源码已移入备份；不能继续宣称 13 个旧 EXE 仍散落活动目录。
- 中文路径本身不是缺陷；应验证 PS5.1 BOM、stdin UTF-8、参数引用和打包解压，而不是统一重命名个人目录。
- capabilities 空数组不能证明缺少 Windows 钩子/托盘权限。官方示例在界面元数据中列 Read/Write，没有这些原生权限枚举。参见 [OpenAI 插件打包文档](https://developers.openai.com/plugins/build/plugins)。
- WPF 标准成像编解码器清单不包含 WebP；未经目标环境验证直接替换 PNG 会增加依赖风险。优先优化尺寸、无损 PNG 或适配的 JPEG，并保留原图。参见 [Microsoft WPF Imaging Overview](https://learn.microsoft.com/en-us/dotnet/framework/wpf/graphics-multimedia/imaging-overview)。

| 阶段 | 工作 | 完成标准 |

| 1：先保证测试、安装可信 | R01、R02，整理当前版本说明 | 测试不触碰真实停用状态；解压包预检成功；缺资源结论一致 |

### 6.1 已用隔离探针确认的安装问题

**R01 从静态风险升级为条件复现。** 在当前 PowerShell 进程中拦截 Test-Path 和 Remove-Item，模拟真实路径下存在 disabled，并执行原 Test-Install.ps1。测试显示通过，但产生了 **3 次指向真实运行路径的删除请求**。全部由模拟函数截获，真实 disabled 文件未创建、未删除。说明“测试通过”目前不能作为测试无副作用的证据。

**新增 R18 / P1：安装就绪等待没有有效总截止时间。** Install-Support.ps1 的 Wait-CodexCompanion 在计时循环内部使用两次 Start-Process -Wait，等待返回之后才检查时限；Install-Startup.ps1 的 --adopt-running 同样没有外部截止时间。

隔离探针将 Get-CodexCompanionProcesses 替换成三个虚拟进程，将 Start-Process 替换成耗时 1.5 秒的成功响应。调用 TimeoutSeconds=1，实际 **3.12 秒后返回 True**。真实进程启动数为 0。这证明超预算仍会返回成功；永久挂起属于对应代码路径风险，本轮没有挂起生产进程来演示。

### 6.2 初始化与事件来源还存在两个边界缺口

**新增 R19 / P2：稳态读取有预算，初始化仍可能长时间阻塞。** BootPlayer.cs:579 在启动路径同步枚举并初始化所有日志；NavigationLogReader.InitialOffset 遇到无换行文件会向前扫描到文件开头。SeedReady 的 512 KiB 字符条件是在 ReadLine 返回后检查，单条巨型行仍可先完整分配。初始化异常按整个 root 捕获，一份文件失败会跳过该 root 后续监听启用。属于静态确认的条件风险，未模拟真实启动卡死。

方案：初始读取也使用预算；历史文件从有界尾部建立基线；单文件失败独立隔离；监听建立和扫描之间安排一次核对，避免初始化窗口漏事件。无换行的历史尾部进入“丢弃至下一换行”状态，不能把残余碎片当成新事件。

**新增 R20 / P2：活动进程验证没有覆盖所有导航事件入口。** BootPlayer.cs:598–640 的 reconcile/event 路径会读取文件并进入 HandleLogLine；TrackNavigationLog 的身份校验仅决定是否加入快速补读列表，ObserveReady 的校验仅决定 UI ready。两者均不阻止无效来源继续解析导航。源时间差只被记录，没有用作事件有效性门槛。

条件：运行后新出现或此前初始化失败的旧日志，其游标从 0 建立；若里面包含合适的旧路由记录，且满足现有去重条件，代码允许派发。不能据此断言本机已经发生历史动画重播。

方案：所有来源统一通过“进程身份、日志世代、启动基线、事件时间与窗口归属”检查；身份结果由活动进程快照缓存，避免改成每行跨进程查询。缺少身份时记录有限原因码并跳过，不把任意日志当活动窗口。

### 6.3 对上一版方案的进一步限定

- 文件 ID 只能识别替换，不能单独识别同一文件截断后迅速写长。R05 还需要保存游标前短字节锚点并比对；检测到变化时同时清除半行和路由上下文。任意截断重写无法仅靠长度完全识别；测试和文档必须保留该边界。
- 导航行 64 KiB 上限不能直接套给完成日志。CompletionJournal 的 JSON 解析长度配置为 16,777,216 字符；字节上限、解码字符上限、单轮 I/O 上限必须分别定义，超限须产生明确原因码。不能以降低内存为由静默漏掉合法完成事件。
- IPC 的 accepted 仅表示入队；media-clock-advanced 仅表示媒体时钟推进；两者都不等于用户看到了正常画面。
- 资源占用数据来自先前 10 秒样本，本次没有把它冒充新的长期测量。以下性能数字是建议验收目标，不是已经达到的结果。

### 原因与明确取舍
