状态：本地脱敏草稿，未向维护者、社区或外部服务提交。
用途：请维护者协助定位正式消息事件交付阶段；不是已证实的 Codex 缺陷声明。

## 1. 问题摘要

Windows 桌面上的本地视频助手通过正式 UserPromptSubmit 命令钩子接收用户输入，
在本机按规则判断后播放反馈。用户希望发送消息后及时反馈，而不是等模型回复。

实际使用中仍有数秒延迟。已有同轮关联样本显示：从引擎 task_started 到插件
hook-entry 约 11.02 秒；hook-entry 到播放窗口打开约 124 毫秒。同期准备阶段
出现 startup_prewarm WebSocket 超时。该证据将主要等待定位到插件入口之前，
但不足以确定连接、会话准备、事件排队或调度中哪一环负责。

UserPromptSubmit 已配置 async=true。尚未用不含播放器的最小钩子独立复现，
因此请先协助核对事件时序，不将问题直接定性为 Codex、代理或播放器缺陷。

## 3. 已观察到的真实时间线

样本 A：2026-10-04 一条普通聊天输入框发送的实际反馈测试，用户报告等待
“三秒以上”。不是问题卡片回复、不是合成 Hook 调用，也不是新的冷启动测试。
同轮身份只在本机内存中关联，以下删除正文、路径和真实会话/任务编号。

以引擎 task_started 为相对零点，非鼠标点击时刻：

| 相对时间 | 事件 | 解释边界 |
| --- | --- | --- |
| 0 ms | task_started | 已进入引擎处理；物理发送点击时间未精确采集 |
| +10,402 ms | startup_prewarm WebSocket 超时 | 同轮准备期间有连接失败，不证明全部等待均由网络造成 |
| +11,024 ms | 插件 hook-entry | 已有数秒等待发生在入口前；未独立测准进程启动与内部调度的全部阶段 |
| +11,110 ms | 插件派发完成 | 早于插件任务状态写入完成 |
| +11,115 ms | 插件任务状态处理结束 | 该样本未见此阶段数秒阻塞 |
| +11,149 ms | 播放窗口打开 | 入口后约 125 ms；不能说发送后 125 ms |
| +11,233 ms | 媒体打开，有音轨 | 入口后约 209 ms；不等同实测屏幕首像素或扬声器出声时间 |
| +11,457 ms | 视频动态进度检查点 | 入口后约 433 ms；不是精确首帧呈现时间 |
| +13,330 ms | 用户点击跳过 | 现场跳过，非正常播到结尾 |

本表统一按所保留的毫秒时间戳相减；原诊断摘要写“约 124/432 ms”，本表
对应为 125/433 ms。未重新读取原始高精度记录，不推定这约 1 ms 差异的原因，
也不把它作为新的性能测量或夸大计时精度。
桌面同线程 turn/start 请求响应记录 durationMs=88、queueWaitMs=0；这是该
请求的响应/排队记录，不是发送至 Hook 的完整耗时，也不能排除后续准备或
Hook 队列等待。不能推广为“所有发送都没有排队”。

补充证据：

- 当天另外两个关联样本 task_started→hook-entry 约 3.88/6.97 秒，均有同轮
  预热超时记录；对应入口→窗口约 149.6/82.9 ms。
- 已核对的 9 组匹配记录包含合成测试，入口→窗口中位数 97.9 ms、最大
  149.6 ms。它们不是 9 次真实用户端到端验收或跨电脑性能基准。
- 样本 A 视频被跳过以后，同轮模型流仍出现连续超时及 HTTP 回退。这是另一个
  消息连接可靠性现象，不得倒过来将后续重试耗时全部算为此前视频触发延迟。

## 4. 当前结论与未证实项

已支持的结论：上述样本主要等待发生在正式插件入口之前；仅继续扩充词库、
调整音量或更换视频，不能解释或消除该等待。本机判断不需要模型先回复。

尚未证实：

- 精确的发送点击→桌面接受→引擎接收→准备→事件入队→进程创建各段耗时。
- 同样延迟是否能在移除播放器、任务状态逻辑和其他钩子的隔离环境复现。
- 各阶段的具体因果关系；代理、远端、准备调度和后台钩子队列的责任比例。
- 冷启动首条输入与温机、空闲新轮与处理中追加输入的可比样本。
- 是否存在当前 Windows 桌面支持的、只读旁听且更早交付的逐条用户消息接口。
- 同文连续发送和追加输入的早期事件身份、原 Hook 身份及无漏播/双播关联。

主要体验问题按 P2 对待；另有实际模型消息流超时，应单独按 P1 可靠性调查。
这不等于认定两者同根因，也不等于当前 Codex 已不能启动。

## 5. 正式接口边界

UserPromptSubmit 有 prompt 和活动 turn_id；async=true 表示后台执行。后台
钩子最多每会话并行 8 个，额外调用等待；本例没有证据证明达到该上限。
异步配置不应被当成“提前派发”开关。见[官方 Hooks 文档](https://learn.chatgpt.com/docs/hooks)。

app-server 提供 userMessage 项和 item 事件，但 thread/read 不订阅事件；
turn/steer 追加到同一活动任务，不发新 turn/started。不能仅按活动 turn_id
识别每次发送。见[官方 App Server 文档](https://learn.chatgpt.com/docs/app-server)。

当前尚未验证插件可安全接入这些事件、其时序一定早于 Hook，或其 item.id
能满足所有追加输入去重。默认 stdio 是桌面通信流，本调查没有接管/分流它。
控制套接字命令存在不代表本机有可订阅端点；未切换传输、启动 daemon、
恢复当前线程或修改桌面应用包。

## 7. 供维护者使用的最小复现方案（尚未执行）

建议在隔离诊断环境先去掉播放器依赖，用单个受信任的 UserPromptSubmit
命令处理器：进入时记录固定阶段和时间，消费 stdin 后正常退出；不播放、
不匹配辱骂、不等待模型、不保存 stdin 或正文/正文哈希。后台配置保持
async=true、timeout=10 秒。本报告没有把这种诊断 Hook 装到用户电脑。

要分开采集：

| 测试 | 做法 | 要确认的点 |
| --- | --- | --- |
| 空闲新轮 | 普通输入框发送无敏感内容的固定测试句 | 接受输入至 Hook 的时序；不能以模型回复到达代替 |
| 处理中追加 | 模型任务进行时追加测试句 | 每条接受事件是否交付，不能要求出现新 turn/started |
| 同文连续发送 | 连续两次同一句，确认均已被桌面接受 | 各自关联号，不因文字相同或共享活动任务号漏计 |
| 冷启动首条 | 保存工作后，在隔离环境完整退出/重开，再发首条 | 与温机差异及启动安全；不在正在工作的用户实例强行重启 |

计时观察器先报告 ready，确认仍在限时窗口内再发送；超时自动结束，不为
取样留下常驻监听。源事件时间、首次实际可读时间、进程创建、Hook 入口和
窗口/媒体时间应分开。没有新样本就标“未验证”，不将缺样本写成漏事件。
这一流程是未来验证建议，不是已经通过的最小复现或本轮测试结果。

## 10. 对应公开版本的调用顺序核验（2026-10-05）

读取官方 openai/codex 的 rust-v0.160.0 标签，解引用至提交
`a956835d020762cb2b570053af06f643a11c0ecc`。与本机 CLI 的版本号一致，
但没有比对可执行文件的构建来源，因此不能说公开源码逐字等于桌面私有构建。
本节是静态实现证据，不是新的用户端到端测量，也没有运行或修改下载的源码。

普通任务路径的明确顺序是：

1. `RegularTask::run` 发出 TurnStarted，执行启动生命周期贡献者。
2. 等待 `consume_startup_prewarm_for_regular_turn`，之后才调用 `run_turn`。
3. `run_turn` 还会先做上下文及工具准备，再调用 `run_hooks_and_record_inputs`。
4. 后者调用 `inspect_pending_input`，才构造并派发 UserPromptSubmit。

因此 async=true 不能跨越这些前置 await。Hook 本地入口后的约 91 ms
与发送后数秒不是同一个区间；继续改本地播放器或关键词没有针对这里的等待。
源码还包含其他前置准备，不能把 15 秒上限当成所有延迟都精确等于 15 秒。

### 等待上限与不能直接使用的配置

预连接 handle 的 timeout 来自 provider 的 `websocket_connect_timeout()`；
未指定时为 15,000 ms。尚未完成的预连接在首次普通任务中等待剩余上限，
超时后才 abort 并返回不可用。这与此前真实样本的首次准备超时位置相符，
但不代替严格因果对照，也不能判定代理承担全部责任。

源码确实有 `websocket_connect_timeout_ms` 字段；这纠正“没有任何超时字段”
这一过宽说法。不过内置 openai 的配置合并使用 `entry(key).or_insert(provider)`，
不会替换已存在的内置提供方。往 `[model_providers.openai]` 写短超时不构成有效修复。
另建自定义提供方会改变连接选择，且此前桌面试用没有得到有效 provider 的
确定证据；不重新未经核验部署这一方案，不改变认证、线路、历史或当前会话。

### 根治方向与本轮结果
